## 0. 요약 (Executive Summary)

**원인**: 7월 305,690원 중 **출력(output) 토큰이 254,915원 = 83%**. 입력은 22,527원(7%)뿐. 즉 "짧은 프롬프트 → 거대한 출력" 구조. 이유 2가지가 곱해짐:
1. **모든 gemini-2.5-flash 호출에 thinking(추론)이 켜져 있음**(코드베이스에 `thinking_budget` 설정 전무). 2.5-flash는 **추론 토큰을 출력으로 과금**(입력의 ~8배 단가). 분류·추출처럼 추론이 불필요한 작업도 매번 추론 토큰을 태움.
2. **공고당 "무제한 출력" flash 호출이 2번**(정밀분석 A1 + 자격추출 A2) 독립 실행 + **재시도 루프**. 7월은 신규 공고가 **8,898건(6월 3,208의 2.8배)** 로 급증 → 출력 토큰 폭증.
3. **토큰 사용량 로깅이 전무** → 어느 흐름이 얼마 쓰는지 관측 불가(=통제 불가).

**즉효 3대 조치**: ① 배치/분류/추출 호출 `thinking_budget=0` ② 무제한 출력 2곳(A1·A2)에 `max_output_tokens` 상한 ③ 모든 호출을 거치는 **중앙 래퍼 + usage_metadata 로깅**(관측). 정확한 절감률은 로깅 후·다음 청구서로 확정.

## 2. 근본 원인 3가지

1. **thinking 전면 ON**: 분류·추출·상담·보고서 모든 flash 호출이 기본 추론. 추론 토큰=출력 과금. 짧은 프롬프트 대량 호출(분류·자격추출)에서 특히 낭비.
2. **무제한 출력 배치 2패스(A1·A2)**: 상한 없음 + verbatim "요약금지" 프롬프트 → 호출당 출력이 큼. 두 패스가 같은 full_text를 각자 읽음(중복).
3. **관측 부재**: 로깅이 없어 스파이크(7월 공고 급증)·낭비를 사후 청구서로만 인지. 통제 불가.

## 3. 모니터링 체계 (근본) — "측정 없이는 통제 없다"

### M1. 중앙 호출 래퍼 + usage_metadata 로깅 (최우선)
- 신규 `gemini_call(flow_tag, model, prompt, config)` 헬퍼 하나로 통일. 응답의 `usage_metadata`(`prompt_token_count`, `candidates_token_count`, **`thoughts_token_count`**=추론, `total_token_count`)를 **`ai_usage_log`** 테이블에 flow_tag·model·일시와 함께 기록.
- 효과: **흐름별·일별 토큰/추정비용 귀속** + **thinking이 실제로 얼마인지 정량화**(지금은 추정). 래퍼가 thinking·상한 정책을 **중앙 강제**하는 지점도 됨.
- 점진 적용: 배치 고volume 호출(A1·A2·A3)부터 래핑 → 인터랙티브로 확대.

### M2. 일일 AI 비용 라인 → AI COO 메일
- `ai_usage_log`에서 어제 토큰·추정비용을 흐름별 집계 → 기존 일일 COO 보고서(매출/크레딧 섹션 옆)에 "AI 비용" 라인. 스파이크 조기경보(7월 급증 같은 걸 그날 인지).

### M3. Google Cloud 예산 알림 (대표, 콘솔 1회)
- Billing → 예산 및 알림 → 월 예산(예: 15만원)+50/90/100% 이메일. **하드 백스톱**(코드 무관). 유일하게 대표 콘솔 작업.

### M4. 관리자 비용 대시보드(선택)
- `ai_usage_log` 기반 흐름별/일별 토큰·비용 조회 엔드포인트. M1이 있으면 저비용 부가.

## 4. 감축 레버 (우선순위 = 영향 × 저위험)

| 우선 | 레버 | 무엇 | 기대영향 | 위험 |
|---|---|---|---|---|
| 🔴1 | **thinking_budget=0 (배치/분류/추출)** | A1·A2·A3·profile·schema·enrich 등 추론 불필요 호출에 추론 끄기 | 출력토큰 대폭↓ | 낮음(추출 품질 무영향) |
| 🔴2 | **무제한 출력 상한** | A1·A2에 `max_output_tokens`(예 A1 4096, A2 2048) | 폭주 방지 | 낮음(초과분 절단 점검) |
| 🔴3 | **usage_metadata 로깅(M1)** | 관측 확보 | 이후 정량 통제 | 없음 |
| 🟠4 | **A1+A2 통합 1패스** | 같은 full_text 두 번 읽는 두 호출을 1 호출로(정밀분석 결과에 eligibility 포함) | 공고당 무제한 flash 2→1(≈50%↓) | 중(프롬프트·파서 재작성) |
| 🟠5 | **response_schema 강제** | A1·A2를 구조화 출력(스키마)로 → 장황·잡토큰↓, verbatim 필드 최소화 | 출력↓+파싱안정 | 중 |
| 🟠6 | **모델 라이트화** | 분류(A3)·단순추출은 `gemini-2.5-flash-lite`(더 저렴) | 단가↓ | 낮~중(품질 A/B) |
| 🟡7 | **Batch API(50% 할인)** | A1·A2·A3는 실시간 불필요 → Gemini Batch API 비동기 제출 | 해당분 단가 −50% | 중(파이프라인 개편) |
| 🟡8 | **컨텍스트 캐싱** | 반복되는 대형 시스템프롬프트/지식 컨텍스트 캐시 | 입력↓(입력은 이미 소액이라 후순위) | 중 |
| 🟡9 | **재시도 상한·빈응답 조기중단** | A1 3+백오프5, A2 400/일 → 빈응답 반복 방지 | 낭비호출↓ | 낮음 |
| 🟢10 | **임베딩 절감** | 섹션 임베딩 N개→핵심만, 재임베딩 배치 남용 금지 | 소액(9%↓ 여지) | 낮음 |
| 🟢11 | **인터랙티브 상한 재검토** | pro_announce 16384/8192, consult 8192 캡 현실화 | 소~중(저volume) | 낮음 |

> 핵심: **🔴1·2·3만으로도 "출력 83%"의 상당부분을 즉시 겨냥**. 🟠4·5·6은 구조적 절감(공고당 호출 반감 + 라이트 모델). 🟡7 Batch API는 큰 폭이나 개편 필요.

## 5. 권장 롤아웃 (3단계)

- **Phase 1 (즉효, 1~2일)**: M1 로깅 헬퍼 + 🔴1 thinking_budget=0(배치/분류/추출) + 🔴2 A1·A2 출력 상한 + 🟡9 재시도 상한. 배포 후 **다음 청구서 + ai_usage_log로 실제 절감 검증**.
- **Phase 2 (구조, 1주)**: 🟠4 A1+A2 통합 1패스 + 🟠5 response_schema + 🟠6 분류 flash-lite A/B. M2 COO 일일 비용 라인.
- **Phase 3 (심화)**: 🟡7 Batch API(배치 분석 50%↓) + 🟡8 캐싱 + 🟢10 임베딩 최적화. M3 예산알림(대표)·M4 대시보드.

## 6. 정직한 한계
- **절감률 수치는 지금 확정 불가**: 토큰 로깅이 없어 "thinking:실출력" 비율이 미기록. Phase 1의 M1 로깅을 넣어야 정량화되고, 실제 효과는 **배포 후 다음 달 청구서**로 확정된다("~% 줄 것"은 추정, "줄었다"는 청구서로).
- 구조상(출력 83% + thinking 전면 ON + 무제한 2패스 + 7월 공고 급증)은 확인된 사실이며, 감축 여지가 큰 것은 분명.
- thinking을 끄면 **추론이 실제로 도움 되는 소수 흐름**(자금상담 심화 등)은 품질 확인 후 선별 유지.
